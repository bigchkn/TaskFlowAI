# TaskFlowAI: AI-Native Task Management

TaskFlowAI is a specialized task management engine designed to bridge the gap between high-level project goals and granular execution by AI agents. It prioritizes machine-readability for agents while maintaining perfect legibility and control for humans.

## Core Philosophy

- **Metadata Decoupling**: Strictly separates machine-readable state (TOML fragments) from human-readable narrative (Markdown roadmaps).
- **Scalable State**: Prevents "context explosion" by archiving completed milestones into `.taskflow/archive/`.
- **Git-Native & Fragmented**: Uses modular TOML fragments in `.taskflow/roadmap/` to eliminate merge conflicts and provide clear version history.
- **Verification-Driven**: Built-in validation ensures that tasks and design documents adhere to project templates.

## Architecture & Data Model

- **Project**: Root configuration and milestone index (stored in `.taskflow/roadmap/index.toml`).
- **Milestone**: A collection of tasks and metadata, stored as a fragment (e.g., `M1.toml`).
- **Task**: The main unit of work. Supports hierarchical subtasks (`parent_id`, `subtask_uids`) and tags.
- **TaskFragment**: A collection of tasks, either in a milestone or the backlog.
- **Design**: Documentation linked to tasks (HLD, LLD, RFC).
- **Execution**: Metadata for tracking agent activity (start/end times, agent ID, logs, outcome).

## Key Technologies

- **Language**: Rust (Edition 2024).
- **CLI**: `clap` with `derive` macros.
- **Serialization**: `serde` and `toml`.
- **Deterministic Storage**: `indexmap` is used to ensure TOML keys remain in a consistent order, minimizing git noise.
- **Time**: `chrono` for UTC timestamps.
- **Logging**: `tracing` for instrumentation.

## Building and Running

### Development
- **Build**: `cargo build`
- **Check**: `cargo check`
- **Run**: `cargo run -- <COMMAND>` (e.g., `cargo run -- dashboard`)

### Installation
- **Global Install**: `cargo install --path . --force` or run `./install.sh`.
- **Completions**: `taskflow-ai completions <SHELL>` (bash, zsh, fish).

## Development Conventions

### Deterministic TOML
Always use `IndexMap` for metadata and configuration maps to ensure that the serialized TOML files remain stable across edits. This is crucial for avoiding unnecessary git diffs.

### Fragmented State
Never store all tasks in a single file. Use the `Storage` trait and `FileStorage` implementation to manage task fragments in `.taskflow/roadmap/`.

### Roadmap Synchronization
The Markdown files `ROADMAP_ACTIVE.md` and `ROADMAP_ARCHIVE.md` are **derived state**. They are automatically regenerated by the `sync` command (or any command that modifies state). Do not edit them manually.

### Design-First Development
For any significant feature (TF-X), create a Low-Level Design (LLD) document using `taskflow-ai design init lld "Title" --milestone MX --task TF-X`. Use `taskflow-ai validate TF-X` to ensure the design document meets the required headers.

### Testing & Verification
The project currently relies on manual verification. Follow the "Verification Plan" defined in the LLD for each task.
- **Unit Tests**: Currently minimal/none. New logic should ideally include tests where possible (TODO).
- **Manual Verification**: Run the CLI against the project's own repository (dogfooding) to verify changes.

## Directory Structure

- `src/`: Core logic and CLI implementation.
  - `commands/`: Individual command handlers.
  - `model.rs`: Data structures and serialization logic.
  - `storage.rs`: Fragmented TOML persistence.
  - `roadmap.rs`: Markdown generation logic.
  - `validation.rs`: Template and design document validation.
- `.taskflow/`: Hidden directory for project state.
  - `roadmap/`: Active TOML fragments and `index.toml`.
  - `archive/`: Archived milestone fragments.
  - `templates/`: Task and design templates.
- `docs/designs/`: High-Level and Low-Level Design documents.
- `examples/`: Reference task templates.
